# WP-R11 — Documentation Site (VitePress) - Review

## Findings

1. **P1, confirmed and fixed post-Test** — `site/.vitepress/theme/style.css` (R1, R8, correctness) — The home page's hero title ("Forge, don't vibe.") was **completely invisible** — a serious regression, not a cosmetic issue, first caught only once the user provided real browser testing (Playwright) in `-p9`, since every prior verification method in this chain (build success, `grep` on compiled output) is structurally incapable of detecting "the element exists in the DOM with the right text, but nothing is visually painted." Root cause: `-p7`'s CSS cleanup deleted `--forge-fire-white`, believing it was dead code from the CSS flame system being removed in that same phase, without checking that the (unrelated, still-active) hero gradient also referenced it — an undefined CSS variable with no fallback invalidates the whole declaration using it, and combined with `-webkit-text-fill-color: transparent`, that means a fully invisible title with no error, warning, or visible-but-wrong fallback. Fixed in `-p9`, then a *second* real bug was found during the same fix: the first patch (a hardcoded near-white literal) repaired dark mode but broke light mode identically for a different reason — near-white text has almost no contrast against a near-white page background — confirmed by screenshotting the animation mid-sweep, where the text visibly dropped to near-invisible. Both are now fixed with a theme-aware CSS custom property, re-verified across 12 sampled animation frames (6 per theme). This finding is recorded at P1 because it fully broke the home page's headline for an unknown but nonzero prior duration, not because it remains unresolved.
2. **P2** — `.github/workflows/ci.yml` / `.github/workflows/site-deploy.yml` (R5, R1) — Both the `site:build` CI step and the deploy workflow have only been verified by running their equivalent commands **locally**, not by an actual GitHub Actions run. R5's own acceptance criterion explicitly requires "a CI run shows the step passing, cited as evidence" — that citation does not yet exist, since nothing has been pushed to a remote (correctly out of Build's scope per lifecycle rules — Build does not push without an approved exception). Fix: Test or Ship must push the branch (or otherwise trigger a real workflow run) and cite the actual run before treating R5/R1's "builds ... in CI" clause as fully satisfied; until then this is real, disclosed evidence risk, not silently absent.
3. **P2** — `package.json` / `package-lock.json` (R4, security category) — `npm audit` reports 3 vulnerabilities (2 moderate, 1 high) in `esbuild`/`vite`, pulled in transitively by the new `vitepress` devDependency (GHSA-67mh-4wv8-2f99). Re-confirmed directly this Review, not just taken from Build's note. Scope is dev-server-only (`vitepress dev`, not `vitepress build`'s output) and no fix is currently available upstream. Fix: Ship must explicitly record or waive this — a non-clean `npm audit` should not ship silently, even when the practical risk is low and the finding is inherited from the ecosystem rather than a mistake in this work.
4. **P3, confirmed and fixed post-Review** — `site/index.md` (R1, R8) — This finding's original text (below, preserved for the record) predicted exactly this class of gap in general terms; the user then found a concrete instance of it by running the site locally: the home page rendered with the full 3-column doc shell (nav + sidebar + content + TOC) instead of the sidebar-free hero layout both design sources show. Root cause: Phase 3 applied CSS tokens only and never set `layout: home` on `site/index.md`. Fixed in `workflow/artifacts/tasks/wp-r11-docs-site-v1-p4.md` — `site/index.md` now uses VitePress's `layout: home` with `hero`/`features` frontmatter; verified via direct build-output inspection (`grep -c "VPSidebar" site/.vitepress/dist/index.html` → `0`; same check on `install.html` → `1`, confirming the fix is scoped correctly). Original finding text: the "visually matches the design mockups" half of R8's acceptance criterion was verified only by inspecting the built CSS/HTML for specific token values (ember hex, Geist font-family, dark-mode default) — no browser screenshot or rendered visual diff against `Agentsmyth Docs.dc.html` was possible in this session (no such tool available). Residual: this fix closes the layout-structure gap specifically; a full pixel-level visual comparison still has not been performed — see Residual Risk.
5. **P3** — `site/.vitepress/config.ts`, `site/.vitepress/theme/index.ts` (R8, maintainability) — No dedicated TypeScript type-check step exists for these two files; correctness currently rests on `vitepress build`'s own esbuild-based transpile succeeding, which catches syntax and VitePress-config-shape errors but not all type errors. Not a defect — there is no `tsconfig.json` in `site/`, and none is required by any manifest ID — but worth naming as a real, if small, gap rather than silently assuming full type safety.
6. **P2, confirmed and fixed post-Review** — `site/.vitepress/theme/ForgeBackground.vue` (R1, R8, performance) — The `-p7` port called `shadowBlur` and/or `createRadialGradient` on every particle, every frame — both real, well-documented expensive canvas operations. With up to a few hundred particles at 60fps, that's tens of thousands of expensive calls per second, which the user confirmed as actual lag in a real browser. Root cause, not just re-tuning: fixed in `-p8` by pre-rendering each fire-color stop as a small offscreen sprite once at mount and using `drawImage` (a cheap, cached-bitmap blit) per particle per frame instead, plus batching draws by composite mode and lowering the DPR cap. Re-verified this Review: zero real `shadowBlur` calls remain in source (comment only); `createRadialGradient` appears only inside the one-time sprite-baking function, not in the per-frame loop; `drawImage` is present in the compiled bundle. **Residual, stated honestly, not glossed over: neither `-p8` nor this Review could measure actual frame rate or CPU/GPU cost — no browser or profiler is available in this environment.** The fix is justified by well-established facts about relative canvas-operation cost, not by a before/after measurement. See Residual Risk.
7. **P3, tooling defect (out of scope to fix here)** — `src/workflow/validators/check-scope-fence.mjs` (lifecycle category) — Found while landing `-p5`: the validator reported `ok` for 3 files (`site/public/logo.svg`, `site/public/favicon.svg`, `site/.vitepress/theme/Layout.vue`) that were not actually declared in the plan's Phase 3 `Touches` line at the time. Root cause: the validator's phase-boundary regex expects `Work:`/`Exit gate:` labels directly preceded by whitespace, but this repo's own convention prefixes them with a `- ` bullet dash, which the regex's `\s*` does not match — so for a plan's *last* declared phase specifically, the Touches capture runs unbounded to the end of the document, sweeping in unrelated backtick-quoted prose (here, a bare `` `site/` `` mention) that then falsely matches as a covering directory prefix. Confirmed by manually replicating the regex outside the tool — not a one-off fluke. Fix: not applied here — `src/workflow/validators/` is explicitly out of scope for WP-R11 per the brief's Non-Goals. Handled instead by manually correcting the plan's Touches list regardless of the tool's (unreliable) verdict; flagged here for Reflect to convert into a real follow-up work item.
