## Implementation Log

### Phase 1 - `prepare` command; remove `--system`

- Extracted the former `isSystem` block's body into `runPrepare(pkgRootDir)`, dropping the
  `writeDefinitionsRoot(cwd, ...)` call so `prepare` writes zero repo-level files (per R1).
  `runPrepare` returns `{ globalDir, version }` for future callers (Phase 2/4) to use without
  re-deriving `defsRootValue`.
- Added `if (command === 'prepare') { runPrepare(pkgRoot); process.exit(0); }` after the
  `check` command block.
- Deleted the `initArgs`/`isSystem` variables and the entire `if (isSystem) { ... }` block.
- Added an explicit guard in the `init` path: `process.argv.slice(3).includes('--system')`
  now prints `agentsmyth: "init --system" was removed. Use "agentsmyth prepare" for a
  global-only install.` and exits 1, rather than silently falling through to a full bare-init
  interview (chose explicit rejection over silent fallthrough — a stale `--system` invocation
  should not look like it worked, consistent with the error-surfacing principle from the
  brief's Q1 resolution).
- Updated `bin/agentsmyth.mjs:93`'s skew-warning text (`Run "agentsmyth prepare"...`) and the
  `help` command list to include `prepare`.
- Fixed the now-stale `# Created by agentsmyth init --system` comment inside
  `writeDefinitionsRoot()` to `# Created by agentsmyth init (linked to a global install)` —
  in scope since it's the same file's stale `--system` text (RI2), low-risk single-line fix.
- Did not touch `bin/agentsmyth.mjs:18`'s comment about `init --system` and polyrepo-member
  first-init behavior — that describes behavior Phase 2 changes (bare `init` becomes the
  first writer of `definitions_root`), so updating it belongs with Phase 2's edit, not here.

### Phase 2 - `init` links to the global install, surfaces failures

- Inserted the auto-link block right after the `.agentsmyth/` already-exists guard and
  before bundle staging: check `~/.agentsmyth/workflow/` existence, call `runPrepare()`
  in-process (not a subprocess) inside try/catch on miss, then unconditionally call
  `writeDefinitionsRoot(cwd, globalWorkflowDir, version)` — reusing the exact function WP-R2
  already shipped, since `writeDefinitionsRoot` already handles the "repo-profile.yaml
  doesn't exist yet" case by creating a minimal stub with just `definitions_root` +
  `agentsmyth_version` set (confirmed by reading the function before reusing it).
  On a caught error: print the underlying `err.message` plus a pointer to re-run `init` or
  run `prepare` directly for the full error, exit 1. `runPrepare()` itself throws naturally
  (no internal try/catch) since its `fs` calls are synchronous and unguarded — no new error
  handling needed inside it.
- Updated `resolveExistingRepoRoot()`'s header comment (line ~18) — it previously said "a
  polyrepo-member's very first `init --system`" has no repo-profile.yaml yet; now `init`
  itself (not just the removed `--system`) is the first writer, so the comment needed a
  one-line correction, not a rewrite.
- `src/setup/SKILL.md` changes (Step 5b rewrite, Phase 3 note, Global Install Note rewrite)
  as scoped in the Repo Impact Map — the core insight driving this split (confirmed by
  re-reading the file rather than assuming): Step 5b's existing `workflow/config/` carve-out
  already establishes the exact pattern needed; only had to extend the same conditional
  logic to the definitions files, and add "if not set, defensive fallback" wording since a
  post-WP-R7 `init` should always have `definitions_root` set by the time Step 5b runs, but
  the skill shouldn't assume that invariant unconditionally without a written escape hatch.
- Manually verified end-to-end (see Command Results) rather than only reading the diff,
  since this is exactly the two-file-drift risk the Plan's Risk Register flagged.

### Phase 3 - Migration audit/prompt/clean

- Added `STALE_DEFINITION_NAMES` (`skills`, `router.md`, `lifecycle.md`, `rules.md`,
  `schemas`, `validators`), `confirmDeletion()` (gated on `process.stdin.isTTY`, using
  `node:readline/promises` — a Node core module, no new dependency per RI3), and
  `auditStaleDefinitions()` (lists found paths, prompts, deletes only on confirmation, never
  blocks linking either way).
- Wired `await auditStaleDefinitions(cwd)` into the `init` flow between the prepare-ensure
  block and `writeDefinitionsRoot()` — top-level `await` is valid here since `.mjs` is
  natively ESM.
- **Plan-time assumption corrected during Build:** the Plan's Phase 3/Phase 7 exit-gate
  wording described testing accept/decline via "piped stdin" (`echo "n" | ...`). Manual
  verification (see Command Results) showed this is not what happens — a piped stream is not
  a TTY, so `confirmDeletion()` correctly takes the fail-closed non-TTY branch even when `y`
  is piped in. This is a **better** security property than originally assumed (a CI script
  can't accidentally auto-confirm a destructive prompt just because something was piped to
  stdin), but it means piped stdin cannot exercise the actual accept/decline branches for
  automated testing — only a real TTY (or a pty) can. Verified all three real behaviors
  directly via a throwaway pty-based Python harness (not part of the shipped codebase) in
  `/tmp` (not committed): decline leaves files in place and still completes the link; accept
  deletes exactly the audited paths and preserves unrelated files (tested with a planted
  `workflow/README.md` alongside the stale paths — confirmed it survived); non-TTY fails
  closed with exit 1 and lists the exact paths, even with `y` piped. This finding changes
  Phase 7's test-harness design (see that phase's log) but does not change R7's required
  behavior — the implementation satisfies the brief/plan's actual acceptance criteria as
  written; only the *testing method* description needs correcting, which is a Build-time
  verification detail, not a scope change requiring a Plan revision.

### Phase 9 - Review fix: adapter gates resolve `definitions_root`

- Root cause (Review's P1-01): none of the 5 per-repo adapter gate templates, nor the root
  `AGENTS.md` template, had any awareness of `definitions_root` — they hardcoded
  `workflow/router.md` as a bare repo-relative path. Phase 2's Step 5b change (this same
  chain) means that file is deliberately never created locally once a repo links — so the
  actual AI agent reading its own gate instructions would find nothing.
- Added a runtime-conditional fallback to all 6 templates: read the local path if present,
  otherwise read `definitions_root` from `workflow/config/repo-profile.yaml` and read the
  corresponding path there instead. Chose this over a build-time `{{TOKEN}}` (Review's other
  named option) because the instruction text is identical regardless of link state — it's
  the agent, not the renderer, that needs to branch at read-time, so no
  `token-map.md`/`config-map.md` change was needed.
  `src/assets/AGENTS.md` needed the broadest edit since it separately references
  `lifecycle.md` and the `skills/` tree, not just `router.md`/`agent-behavior.yaml`.
- P3-01: removed `runPrepare()`'s `return { globalDir, version }` and its comment. Considered
  wiring the return value through both call sites instead (the user's stated default
  preference) but pushed back: the "global install already present" branch in both `init`'s
  auto-link block and `headlessBootstrap()` never calls `runPrepare()` at all, so both call
  sites need their own independent `globalWorkflowDir`/version computation regardless of
  whether `runPrepare()` ran — wiring the return value through would only save one
  `JSON.parse`/`readFileSync` pair in the "did run" branch while adding an `if`/`else` split,
  a net complexity increase for a trivial saving. User accepted scoping it out.
- Verified: `grep -c definitions_root` on each of the 6 templates returns ≥ 2 (confirms the
  fallback text landed in every file); `node --check bin/agentsmyth.mjs` passes;
  `npm run build && npm run validate && npm run violations:test` all pass; the full existing
  test matrix (`setup-checks`, `setup-refs`, `conformance`, `root-resolution`) and the new
  `init-prepare-interop:test` suite (32/32) all still pass after both fixes.
- Not independently verifiable by any script in this repo: whether a real AI agent, given
  the new conditional instruction, actually follows it correctly end-to-end in a freshly
  linked repo. This is the same class of unprovable-by-script risk that already applies to
  every other line in every adapter gate (nothing in this repo mechanically proves an agent
  follows *any* gate instruction) — not a new risk this fix introduces, but worth Test-phase
  manual QA attention given how central this particular instruction is.

## Architecture Notes

- role: Senior Engineer
- decision: `runPrepare()` returns `{ globalDir, version }` even though Phase 1 has no
  caller that uses the return value yet — Phase 2 and Phase 4 both need `globalDir`
  (equivalently `defsRootValue`) and `version` to call `writeDefinitionsRoot()`, so exposing
  them now avoids re-deriving `join(homedir(), '.agentsmyth', 'workflow')` in three places.
- constraint: `prepare` must write zero repo-level files (R1's acceptance) — verified by
  running it with `cwd` pointed at this repo and confirming `git status` showed no new
  tracked-tree changes outside `bin/agentsmyth.mjs` itself.
- tradeoff: Considered letting `agentsmyth init --system` silently fall through to a normal
  bare `init` (simplest diff) vs. an explicit rejection — chose explicit rejection so a user
  running muscle-memory `--system` gets pointed at `prepare` instead of unknowingly running
  a different, un-requested command (a full interview instead of a global-only install).
- downstream: Phase 2 will call `runPrepare()` from bare `init`'s auto-link path and must
  wrap the call so a thrown error (e.g. an unwritable `$HOME`) is caught and surfaced per
  R2's acceptance criteria, not left to crash with a raw stack trace.
- decision (Phase 2): reused `writeDefinitionsRoot()` verbatim rather than writing a
  init-specific variant — it already handles "no existing repo-profile.yaml" by creating a
  minimal stub, which is exactly what bare `init` needs before the interview populates the
  rest of the file.
- constraint (Phase 2): `src/setup/SKILL.md`'s Step 3 config-writing step must not clobber
  the `definitions_root`/`agentsmyth_version` the CLI already wrote — added an explicit note
  rather than relying on the agent to infer this from the file already existing.
- downstream (Phase 2): Test/Ship must exercise the full agent-driven setup skill at least
  once end-to-end (per the Plan's Risk Register) — Build's automated/manual checks here only
  cover the CLI boundary (repo-profile.yaml stub + `.agentsmyth/` staging), not the
  agent-driven Phase 3-5 interview and expansion, which no Node script can simulate without
  a real agent session.
- decision (Phase 3): gate the deletion prompt on `process.stdin.isTTY` rather than
  attempting to detect "was something meaningfully piped in" — a real TTY is the only signal
  that cannot be spoofed by an unattended script, matching the same fail-closed philosophy
  R2 established for prepare-failure surfacing.
- downstream (Phase 3): Phase 7's automated test harness cannot exercise the accept/decline
  branches via simple piped stdin (confirmed non-TTY, fails closed) — it must either accept
  reduced automated coverage for those two branches (relying on Test-phase manual QA,
  already scoped in the Plan's Risk Register) or use a pty. Recorded as an open design point
  for Phase 7, not resolved here.
- decision (Phase 4): `headlessBootstrap()` calls `writeDefinitionsRoot()` after the stub
  `repo-profile.yaml` is already written (in the `for` loop), rather than duplicating the
  `repository:`/`learnings_sessions_root:` anchor-matching logic — confirmed by testing that
  `definitions_root` lands correctly right after the template's `learnings_sessions_root:`
  line.
- downstream (Phase 4): the global-install-ensure block runs before `mkdirSync(configDir)` —
  a `prepare` failure here leaves zero stub files written, matching R2's "no partial state"
  guarantee for the equivalent `init` path.
- decision (Phase 5): combined the R4 skew-resolution doc note and the R5 invariant note into
  one subsection of `docs/knowledge-map/repo-mental-map.md` rather than writing them
  separately in Phase 5 and Phase 6 — same target location, no reason to touch the file twice.
- downstream (Phase 5): the two RI2 references the Plan didn't list
  (`src/workflow/validators/lib.mjs`, `scripts/render-adapters.mjs`) are a reminder that
  Repo Impact Map greps done at Plan time can miss references introduced or discovered later
  — Review should re-run the repo-wide `--system` grep independently rather than trusting
  this task artifact's list as exhaustive.
- decision (Phase 9): fixed the P1 finding as a runtime-conditional instruction inside the
  gate templates rather than a build-time token — this is a genuinely different mechanism
  than everything else Step 5a.1 renders (all existing tokens are per-repo config values
  substituted once at setup time; this one needs to branch on runtime state — whether
  `workflow/router.md` exists — that setup-time rendering can't know in advance for a repo
  that might get migrated later).
- constraint (Phase 9): this fix could not be verified by any script — a Node test can
  confirm the instruction text exists and is well-formed, but only a real AI agent session
  can confirm the agent actually follows a "read X, or if absent read Y" instruction
  correctly. Flagged for Test-phase manual QA, not silently claimed as fully verified.
- downstream (Phase 9): Ship's R6 Notion handoff (Phase 8) should mention this fix when it
  describes what shipped — it's a materially different (and better) answer than what page 10
  originally described for Scenario B, since the original scenario draft predates the
  discovery that the linked model breaks agent-side gate discovery without this fix.
